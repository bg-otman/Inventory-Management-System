# Inventory · المخزون

**A clear view of your stock, invoices, and balances.**

Inventory is a simple online stock and accounts application with English and Arabic interfaces. This revision adds required product suppliers, visible sales cost references, and removes all tax controls and calculations.

## What is delivered

- **Next.js + TypeScript + Tailwind frontend:** a responsive dashboard, stock, sales, purchases, customer and supplier accounts, and settings. Arabic switches the interface to RTL. Each invoice keeps its selected language.
- **FastAPI + SQLAlchemy + PostgreSQL backend:** authenticated sessions, roles, stock movements, invoices, payments, allocation, and audit activity. Alembic owns schema migrations.
- **Interactive sample preview:** the default frontend build uses sample data saved in the current browser. It is a UI/workflow demonstration; it is not a shared business database. Reset it or start empty in Settings.
- **Production deployment source:** Docker Compose, Nginx, database initialization, weekly backup worker, and restoration controls. These services are not running inside the hosted sample preview.

The updated agreed requirements are in [docs/SPEC.md](docs/SPEC.md). This README describes what the current source actually implements and how to run it.

## Quick start

The simplest way to run the full application is:

```bash
make
```

The default target generates `.env` when needed, creates the local `./backups`
directory, builds the images, and starts the Compose stack. Open
<http://localhost:8080> after the `api` and `web` services are healthy. The
generated owner password is printed by `ops/setup_env.py`; save it securely.

Useful commands:

```bash
make ps                 # show service status
make logs               # follow all service logs
make down               # stop and remove containers (keep volumes)
make backup             # request a backup from the worker
make test               # run backend and preview checks
make typecheck          # validate TypeScript
```

By default, backups are stored in `./backups`, which avoids requiring
permission to create a directory at the filesystem root. For a deployment
with a dedicated private backup mount, pass it explicitly:

```bash
make BACKUP_DIR=/mnt/private/inventory-backups
```

## Implemented workflows

| Area | Behavior |
| --- | --- |
| Product creation | Product name, category and supplier are required. Select an existing supplier with its contact details, or create one inline. New suppliers require a name; phone, address and notes can be added immediately or later. Category creation also stays inside the form. |
| Optional details | SKU, barcode, description, starting purchase cost, default selling price, unit and low-stock threshold. Missing codes are NULL, not autogenerated. Provided codes are unique. Barcodes remain text, including leading zeros. |
| Units | One unit per product; defaults to unit. Unit, piece and carton use whole quantities; kg, meter and liter allow three decimal places. No conversions. |
| Warehouses | Stock quantities by warehouse, owner adjustments and transfers, recent movement history. No negative stock. A new product has zero stock. |
| Sales | Show the latest purchase cost and default selling price beside each selected product. Draft or confirmed invoice, immediate or later complete delivery, fixed MAD discount, payment and one due date. |
| Purchases | Complete receipt and invoice confirmation can happen together or separately. Receive goods without a known price, then fill prices and confirm the invoice later. |
| Customers and suppliers | Search by name/phone, view transactions, amounts owed, available deposits, and payments. Customer full name is recorded on the account. |
| Credit and deposits | Named accounts only. Payments can be partly allocated across several invoices for that account; the remainder stays available. |
| Walk-in sale | Automatically paid in full. Select a named customer to leave a balance. |
| Invoice printing | Company/logo/contact, number/date, customer, product lines, totals, payment at issue, due date and delivery date. Print or save as PDF through the browser. Purchases print as purchase records. |
| Barcode input | Keyboard-style scanners work in stock search and the transaction barcode field. Enter selects a matching product or reports an unknown code. Repeat scans increase its quantity. No camera or device-specific integration. |
| Alerts | In-app stock watch and overdue invoice status/filter. The product's threshold applies to each warehouse with recorded stock. |
| Corrections | Owner reverses allocated payments first, then reverses the erroneous transaction; stock corrections and history remain traceable. No full returns/refund module. |
| Settings | Company information/logo, language preference, owner-created employee accounts, backup status/restore. |

A delivery changes physical stock; invoice confirmation establishes the amount owed. Neither printing nor recording a later payment changes stock. Delivery and receipt are each recorded at most once. A pending sale does not reserve stock: availability is checked again when delivered.

Employees can manage products/categories, view purchase costs and change selling prices. Company settings, account creation, warehouse administration, stock adjustments/transfers, reversals and backup/restore are owner operations, enforced by the API.

### Amounts and historical records

- Currency is MAD. Tax inputs, identifiers, settings and printed tax rows are removed.
- Round each quantity × unit-price line to two decimals, sum the lines, then subtract the invoice discount. No tax is calculated or added. The API uses Decimal and ROUND_HALF_UP.
- Invoice numbers are sequential (`INV-000001`); purchases have a separate sequence (`PUR-000001`). Reversed numbers are retained.
- Company, customer, product labels, prices, totals, language and payment-at-issue are snapshotted when confirmed. Later account payments are visible in the account/payment history. The delivery-date annotation reflects actual delivery when recorded.
- An unset price is allowed in the product catalog and a draft. Confirming an invoice requires an explicit price for every line; zero is permitted if intentionally entered.
- Posted transaction details cannot be edited. A received purchase draft can have its costs finalized, but not its supplier, warehouse or quantities.

The sales cost reference uses the latest confirmed purchase line, even if delivery is pending; drafts and reversed purchases are excluded. Until a purchase exists, it uses the optional starting cost on the product. Missing costs display “Not recorded”; explicit zero is valid. The default selling price stays visible while the actual sale price is edited. These internal price references never appear on customer invoices.

## Upgrade from the first version

The application name is now **Inventory / المخزون**. The existing preview URL, database/volume names, cookie names and browser storage key are retained so the rename does not disconnect existing data.

On production startup, Alembic migration `0002` adds the product supplier relationship and optional starting cost. It links old products to their latest confirmed purchase supplier where one is known; other existing products remain intact and require a supplier when edited. New products always require a supplier. Settings are cleaned of tax fields. Previously issued invoice totals and stored historical snapshots are preserved; the API and printed views expose no tax fields. New or reconfirmed draft totals are subtotal minus discount.

Saved browser preview data is upgraded in place, keeping products, transactions and balances. A fresh preview already includes example supplier links and purchase costs. Backup metadata uses schema `0002`; older backups require the matching earlier application version before upgrading.

## Architecture

The browser loads the statically exported Next.js app from Nginx. Requests to `/api/v1` go to FastAPI on the same origin. Only FastAPI and the backup worker access PostgreSQL. A separate worker handles slow backup/restore jobs.

| Directory/file | Purpose |
| --- | --- |
| `frontend/app/`, `frontend/components/` | Next.js pages, dashboard, forms and responsive styles |
| `frontend/lib/i18n.ts` | English/Arabic UI strings |
| `frontend/lib/api.ts` | Production API client and retry identifiers |
| `frontend/lib/demo.ts` | Isolated sample-data adapter used by the preview |
| `backend/app/models.py`, `schemas.py` | Database models and input validation |
| `backend/app/services.py` | Stock, invoice, payment and correction rules |
| `backend/app/main.py`, `security.py` | Routes, sessions, permissions and CSRF protection |
| `backend/app/backups.py` | Weekly backup queue, verification, retention and restoration |
| `backend/alembic/` | Versioned database migrations |
| `compose.yaml`, `Makefile` | Root deployment entry points |
| `frontend/Dockerfile`, `nginx/`, `ops/` | Production deployment and setup |

All business writes run in database transactions. For this small installation, one PostgreSQL row lock serializes them, preventing simultaneous overselling or over-allocation. Retry identifiers reject changed requests and replay previously committed results. There is no offline queue or service worker. Authentication uses server-stored, hashed session tokens, secure HttpOnly cookies, CSRF tokens and scrypt password hashes.

The first API uses one state endpoint for simplicity. Products and transaction histories are loaded together; the UI paginates lists locally. The activity feed shows 50 events and the stock movement view 300 movements; older data remains in the database. Add server pagination before a substantially larger rollout.

## Run the interactive sample

Requires Node.js 22 and npm.

```bash
npm --prefix frontend ci
npm --prefix frontend run dev
```

Open `http://localhost:3000`. No backend or credentials are needed for sample mode. The footer identifies sample mode. The sample is local to this browser and does not implement shared persistence, real authentication, or backups.

```bash
npm --prefix frontend run build
```

This creates the static sample in `out/`. It is the build used for the private hosted preview. `NEXT_PUBLIC_DEMO` is a build-time switch: rebuilding is necessary to change modes.

## Run the actual application

Requires Docker with Compose and Python 3 for the setup helper. The production Dockerfile sets `NEXT_PUBLIC_DEMO=false`, builds Next.js, and serves the result behind Nginx. The database starts with an owner and one warehouse, without demo records.

1. From the project root, generate deployment secrets:

   ```bash
   python3 ops/setup_env.py
   ```

   Save the generated owner password in a password manager. This creates a private `.env` and refuses to overwrite an existing file. Set `OWNER_NAME`, `OWNER_USERNAME` and `BACKUP_HOST_DIR` as needed before first startup. Changing the initial owner variables later does not reset an existing account.

2. Choose backup storage. The default is the project-local `./backups`
   directory and requires no `sudo`:

   ```bash
   mkdir -p backups
   ```

   For a dedicated mount, set `BACKUP_HOST_DIR` in `.env` and create that
   directory with the permissions required by Docker. A folder on the
   application machine alone does not protect against losing that machine;
   replicate backups off-host. Keep database dumps and `.env` out of the
   public web root and source control.

3. Start the services:

   ```bash
   make
   make ps
   make logs
   ```

   PostgreSQL is private. Nginx listens at `127.0.0.1:8080`. Put an HTTPS reverse proxy on the host in front of it and preserve the public Host header. Keep `COOKIE_SECURE=true` for HTTPS. For an isolated localhost trial using HTTP only, set it to `false` in `.env` before starting, then open `http://localhost:8080`.

4. Sign in using the generated account. Set company details, create categories/products and any additional warehouses, then record purchases or owner stock adjustments. Create customer/supplier accounts before credit or deposits.

Do not use `docker compose down -v` on an installation whose database you need to keep; it removes the database and control volumes. Regular `docker compose down` preserves them.

### API development and tests

Python 3.12 was used for validation. The lockfile pins the installed dependencies.

```bash
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.lock.txt
cd backend
PYTHONPATH=. ../.venv/bin/pytest -q
```

To run the API outside Docker, set `DATABASE_URL` to a PostgreSQL connection URL, `OWNER_PASSWORD` to a fresh password of at least 12 characters, and the appropriate cookie setting. Then, from `backend/`:

```bash
../.venv/bin/alembic upgrade head
../.venv/bin/python -m app.bootstrap
../.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

SQLite is only the default for local backend experiments/tests. Production requires PostgreSQL for the locking and backup behavior. Serve the production frontend and API under the same origin as in the provided Nginx configuration; the sample `npm run dev` command intentionally uses demo mode.

## Weekly backups and restoration

The worker creates a backup on first startup and every Sunday at 02:00 UTC, with catch-up after downtime. It retains the four most recent successful normal backups, including manual backups. Recovery snapshots taken before restores are kept separately and require operator retention management.

Each archive is a PostgreSQL custom-format dump, with a SHA-256 checksum, timestamp, schema version and app version in its JSON sidecar. The logo and invoice snapshots live inside the database and are included. The deployment's secrets, database roles and external hosting configuration are not part of the dump; keep them separately.

Owners use **Settings → Backups** to inspect status, request a backup, or select a restore. Restoration requires the owner password and an explicit acknowledgment. It:

1. Checks the archive checksum and matching schema version.
2. Restores into a temporary validation database and verifies key tables, nonnegative stock and an active owner.
3. Places the API in maintenance, waits for active transactions and creates a recovery snapshot.
4. Replaces the live data in one PostgreSQL transaction, then invalidates sessions. Users sign in again using accounts from the restored snapshot.

A failed database restore transaction rolls back. If the worker crashes during restoration, it marks the job failed on restart and leaves any maintenance marker in place. An operator must inspect PostgreSQL state and the job details before clearing maintenance or retrying; the worker never blindly repeats a restore.

Operator actions when the UI is unavailable:

```bash
make logs
make backup
# Destructive: replace the live database with this exact verified snapshot.
docker compose exec backup-worker python -m app.backups restore inventory-TIMESTAMP-ID.dump
```

Use the actual archive name shown in the configured backup directory. Coordinate operator commands with the worker; do not run competing restores or backups. Job details are in the control volume at `/control/jobs`. Test a restore on a separate PostgreSQL installation before putting client data in the system. Weekly snapshots can lose changes since the selected backup; they are not continuous recovery.

## Verification and remaining launch work

Validated in the implementation environment:

- 17 backend tests covering authentication/CSRF, supplier links, optional codes, units, stock atomicity, delayed delivery, receipt before invoice, deposits/multi-invoice allocation, walk-in rules, tax-free totals, money rounding/limits, snapshots/XSS escaping, permissions/reversals, backup checksums/retention and interrupted-job handling, and migration of an existing dataset.
- TypeScript validation and preview data workflow checks (`node frontend/tests/demo-workflows.cjs`).
- Next.js static export build and Alembic schema upgrade on temporary SQLite, including existing invoices and stock.

PostgreSQL/Docker execution, real backup/restore, concurrent PostgreSQL requests, browser layout/RTL behavior and printer/scanner hardware have **not** been verified in this environment. Before client launch, run the supplied Compose stack, exercise simultaneous sales against limited stock, complete a restore drill and review the English/Arabic workflows and printed invoices with the client. This is an implemented MVP, not a claim of production acceptance.

Deliberately excluded: offline mode, unit conversions, partial deliveries, stock reservations, complex invoice matching, multi-currency, expiry/batch/serial tracking, import tools and a full returns module. Opening stock can be entered with an adjustment reason; a dedicated historical opening-debt ledger and backdated opening entries are not included because the current workflow starts from new records. User creation is implemented; account recovery/deactivation management remains operator work in this version.
